## 2. 仮説と判定規則

### 2.1 仮説

- **H1（主）**: スクリーニングで T0 が 0/k だった Task 集合で、同じ Task・同じ条件で T0 を再測定した成功率より、T1 の verified success rate が Δ = 0.30 以上高い。
- **H0**: 差は 0.30 未満。
- **副次（主判定に使わない）**: 成功 1 件あたりの total tokens の T1 / T0、regression rate の差、critical boundary violation の有無、task nature（旧版 U7 と同じく記録のみ）。

**T0 を評価集合で再測定する理由（回帰の対照）**: 「T0 0/k」で選んだ集合には、真の成功率が 0 でない Task が偶然の失敗で混じる。例えば真の成功率 0.2 の Task は k = 3 で 51.2%、0.3 で 34.3%、0.5 で 12.5% の確率で 0/3 になる（計算）。T0 を測り直さずに T1 の成功率だけを見ると、平均への回帰による T0 側の回復を T1 の効果と取り違える。そのため評価では T0 と T1 を同じ Task・同じ rep 数で測り、paired で比べる。スクリーニングの結果は選別にだけ使い、評価の T0 の値には数えない。

### 2.2 判定規則

**完了 Task と欠測**: d_i を計算する Task は、T0 再測定と T1 の両方で rep 3 がすべて完了した Task（**完了 Task**）に限る。1 Run でも欠けた Task（上限・環境起因の中止を含む）は評価から外し、件数と理由を報告する。結果は、この除外後の集合に条件付けた推定として解釈する。これにより全 Task の d_i が同じ分母（rep 3）を持ち、§2.3 の検出力の前提と一致する。

前提（**計測成立**）: 完了 Task が 12 以上、全 Run で実効値が V10 と一致、critical boundary violation の検出が機能している、かつ評価時の T0 再測定の成功率（完了 Task の全 Run での割合）が 0.60 未満（0.60 以上は難度の操作化の失敗。旧版の p_ceiling と同じ扱い）。どれか 1 つでも満たさなければ計測不成立で INCONCLUSIVE とし、D・p・U の値に関係なく支持・棄却を判定しない（判定の優先順位: 計測成立の確認 → 支持 → 棄却 → INCONCLUSIVE。支持と棄却は同時に成り立たない。支持は D ≥ 0.30 を、棄却は U < 0.30 を要し、U ≥ D のため）。

**統計量**: 完了 Task i ごとに d_i =（T1 の verified success 率）−（T0 再測定の verified success 率）（どちらも 3 回中の割合）を計算し、D = d_i の完了 Task 間の平均とする（Task を等しい重みで数える）。同じ Task の rep どうしの相関は d_i にまとめて扱い、block を独立の観測としては数えない。

**検定（Task 単位の符号反転の並べ替え検定）**: 帰無仮説は「各完了 Task で、T1 の 3 Run と T0 再測定の 3 Run の結果の同時分布が、条件のラベルを入れ替えても変わらない（Task ごとに効果なし、交換可能）」という sharp null とする。この下では各 d_i が 0 について対称になり、符号の反転は正確に成り立つ。d_i の符号を全 2^N 通り反転した平均 D* を全列挙し（N = 12 なら 4,096 通り。乱数を使わないので seed は不要）、p = #{D* ≥ D} / 2^N とする（等号を含む。片側）。この p は sharp null に対して正確で、「平均の差 D ≤ 0」という複合帰無仮説全体に対する誤判定率は保証しない（例えば Task ごとに正負の効果が打ち消し合う場合）。したがって p < 0.05 は「Task ごとに効果なし、を 5% 水準で否定した」と読む。

**d_i の離散性**: d_i は 1/3 刻みの値しか取らないため、D ≥ 0.30 でも p ≥ 0.05 になり得る。例: 4 Task で d_i = +1、8 Task で 0 なら D = 0.333 で p = 0.0625（支持にならない）。6 Task で +2/3、6 Task で 0 なら D = 0.333 で p = 0.0156（計算）。

**上限（検定の反転による区間）**: 上限は「d_i − δ が 0 について対称」（全 Task で効果が同じ δ だけずれるシフトモデル）という仮定の下での検定を反転したものとする。d_i は [−1, 1] の 1/3 刻みの値なので、この仮定は厳密には成り立たず、U の被覆率は名目の 95% を保証しない（§2.3 で想定分布の下の被覆率を報告する）。値 δ ごとに e_i = d_i − δ とし、e_i の符号を全 2^N 通り反転した平均 E* と観測平均 E = D − δ を比べ、p_low(δ) = #{E* ≤ E} / 2^N を計算する（帰無仮説 D ≥ δ、対立 D < δ）。δ を D から 0.001 刻みで増やし、p_low(δ) < 0.05 となる最小の δ を **D の片側 95% 上限 U** とする（1 まで届かなければ U = 1）。

| 判定 | 条件 |
|---|---|
| **支持** | 計測成立、かつ点推定 D ≥ 0.30、かつ並べ替え検定の p < 0.05（sharp null の否定）、かつ T1 に critical boundary violation がない、かつ regression rate の差 ≤ 0.10 |
| **棄却** | 計測成立、かつ U < 0.30 |
| **INCONCLUSIVE** | 上のどちらでもない場合。計測不成立（評価時の T0 再測定の成功率 ≥ 0.60 を含む）、評価集合が N に届かない（feasibility-only）を含む |

- 棄却でも「T1 に効果がない」とは言わず、「この条件で Δ = 0.30 以上の効果は確認できない」と報告する。
- 支持でも T1 の標準採用の根拠にはしない。採用は独立 Reviewer の Judgment と Human を経る（設計案 §7）。
- 成功 1 件あたりの token 比は、T0 の成功が 0 件なら定義できないため、その場合は block あたりの total tokens の T1 / T0 を報告する。
- **結論の射程**: 結論は「候補表の順序で処理し、本書の規則で選ばれた評価集合」に条件付けて報告する。評価集合には 25 Run で 0/5 を観測済みの候補 2・3 が入り（§3.1）、budget-excluded の候補は除かれる（§3）。そのため結論を「T0 が解けない Task 一般」や候補表の母集団へ一般化しない。

**推奨の判定方法と理由**: Task 単位の符号反転の並べ替え検定を採る。理由: (1) block を独立に数える McNemar は同じ Task の rep の相関で不確実性を過小評価する。(2) cluster bootstrap の percentile 区間は 12 Task 程度で名目の被覆を保つ根拠がない。並べ替え検定は全列挙で正確に計算でき、乱数にも依存しない。(3) 符号検定も正確だが d_i の大きさを使わず、12 Task では検出力が低い。bootstrap は使わない。

**帰無境界 0 と閾値 0.30 の関係**: 検定が否定するのは「Task ごとに効果なし」という sharp null で、帰無境界は 0。閾値 0.30 は効果の大きさの基準で、点推定 D ≥ 0.30 として別に課す。したがって支持は「Task ごとに効果なし（sharp null）を 5% 水準で否定し、かつ平均の差の点推定 D が 0.30 以上」であることを意味する。平均の差が 0 より大きい、または 0.30 以上であることを統計的に示したものではない。棄却は逆に、シフトモデルの仮定の下で、真の差が 0.30 以上である可能性を 5% 水準で否定できた場合に限る（仮定が崩れる場合の誤判定率は §2.3）。

### 2.3 検出力の近似（N = 12、d_i の分布の仮定は推測）

d_i の分布の仮定（推測、観測なし）: 完了 Task のうち割合 π は「T1 で解ける Task」（T1 の各 Run の成功確率 0.8）、残りは「T1 でも解けない Task」（同 0.1）。T0 再測定の各 Run の成功確率は全 Task で 0.1。rep = 3 で Run は独立。真の差は D_true = 0.7 π。この仮定で、N = 12 の判定規則（点推定 D ≥ 0.30 かつ p < 0.05、および U < 0.30）を各 D_true で 4,000 回ずつ模擬した結果（`python scripts/hard_task_power_sim.py table`、Python 3.12 の `random.Random(20261026)`、6 条件を表の順に同じ乱数列で実行。model は起動していない）。被覆率は U ≥ D_true となる割合:

| D_true（π） | 支持の確率 | 棄却の確率 | U の被覆率 |
|---|---|---|---|
| 0.00（0） | 0.000 | 0.984 | 0.986 |
| 0.15（0.214） | 0.108 | 0.371 | 0.914 |
| 0.30（0.429） | 0.497 | 0.055 | 0.945 |
| 0.40（0.571） | 0.801 | 0.009 | 0.963 |
| 0.45（0.643） | 0.886 | 0.003 | 0.951 |
| 0.50（0.714） | 0.952 | 0.000 | 0.975 |

- **N = 12 の位置づけ**: 想定する真の差 0.40〜0.45 で支持の確率は約 0.80〜0.89（推測の仮定の下）。真の差がちょうど 0.30 の境界では約 0.50 で支持され、0.30 を僅かに超える効果の検出は保証しない。真の差 0.15 程度の小さい効果は棄却されやすい（約 0.37）ので、棄却を「効果がない」と読まない（§2.2）。
- **シフトモデルが崩れる場合の U**: この想定分布は Task ごとに効果が異なる（シフトモデルに従わない）。被覆率は 0.914〜0.986 で、D_true = 0.15 では名目の 0.95 を下回る。真の差がちょうど 0.30 のときに誤って棄却する確率は 0.055 で、名目の 0.05 をわずかに超える（模擬誤差の範囲内かは区別できない）。両極端の分布（T1 で解ける Task では T1 が必ず成功し、それ以外の Task と T0 は必ず失敗）では、真の差 0.30 のときの誤棄却の確率は約 0.087 まで上がりうる（独立レビューの模擬を Agent が再実行して確認、R = 2000、seed 1。`python scripts/hard_task_power_sim.py false-reject` の `1.0/0/0 Dtrue=0.30` の行。3 種の分布を同じ乱数列で順に実行するため、順序を変えると値が変わる。model は起動していない）。U は近似の上限として扱い、棄却を報告するときは U の値と「シフトモデルの仮定の下」を必ず併記する。
- 4,000 回の模擬のため各確率には ±0.016 程度（95% の目安）の誤差がある。計算の要点: 各 Task で π の確率で T1 の成功確率 0.8、それ以外は 0.1、T0 は 0.1 として 3 Run ずつ Bernoulli を引き、d_i × 3 の整数値の符号反転の分布を全 4,096 通り分の動的計画で正確に数えて p と U（0.001 刻み）を求める。d_i の分布が仮定と違えば（例: T1 の成功確率が Task ごとに連続的にばらつく）値は変わる。計算スクリプトは [scripts/hard_task_power_sim.py](../scripts/hard_task_power_sim.py)（標準ライブラリのみ。引数なしで表・§2.2 の離散性の例・誤棄却をすべて出力する）。
- N = 12 は計測成立の下限で、検出力の保証ではない。

## 3. スクリーニング

- **手順**: 候補表の初回候補を `order` の昇順で処理する。各候補で T0 を最大 k = 3 回実行し、verified success が 1 回でも出たらその候補は打ち切って除外する（以降の Run をしない）。3 回とも失敗した候補を評価集合に入れる。0/k の候補が N = 12 件そろった時点でスクリーニングを止める。初回 44 件を使い切っても、またはスクリーニング全体の上限に達しても 12 件に届かなければ、評価は feasibility-only とする（予備の追加はしない。V6 は推奨値を採り、代替案の予備 44 件への拡大は採らない）。
- **除外の区別**: 1 Run の上限・1 候補の上限・wall clock 上限で止まった Run は「失敗」に数えず、その候補は **budget-excluded** として別記録し評価集合に入れない（成否が分からないため）。環境起因の中止も同じ扱い。費用の大きい Task ほど除外されやすく、評価集合が変わり得るため、budget-excluded の件数・理由・その時点の消費を報告し、結果は「除外後の集合に条件付けた推定」として解釈する（成功率の推定に除外の影響を混ぜない）。
- **k = 3 の根拠**: 打ち切りがあるため成功する候補の費用はほぼ 1 Run で済み、費用の大半は 0/k の候補に掛かる。k = 2 では真の成功率 0.3 の Task が 49% の確率で 0/2 になり、回帰の混入が増える。k = 5 は旧版と同じだが費用が 5/3 倍。推測。
- **止める規則が結果を利用しない理由**: 止めるかどうかは T0 の結果（選別基準）だけで決まり、T1 の結果は見ない。候補の順序は較正前に固定済み（候補表、blob `aad6f23629efaefdd266f0e21ca59248e4693c7b`）。

### 3.1 今回の 25 Run の扱い（推奨: 再利用）

**規則**: 最初の 5 候補は、新版のスクリーニングを済ませたものとして扱う。判定には各候補の **Run 番号の小さい順の最初の k 回（n1〜nk）** だけを使い、n(k+1) 以降の Run は使わない。この規則は 5 候補すべてに同じに適用し、候補ごとに使う Run を選ばない。

- k = 3 での結果: 候補 2・3 は n1〜n3 がすべて失敗で **選別**。候補 1（n1〜n3 成功）・候補 4（同）は除外。候補 5 は n1〜n4 が成功、n5 が失敗で、n1〜n3 に成功があるため除外（25 Run の最終データ: Operator のローカルの各 Run の `run.json` の `verifiedSuccess`。集計は #244 の 2026-10-25T19:51:23Z のコメントで 4/5）。
- **結果を見て有利に選んでいないことの確認**: 候補 1〜4 の選別結果は k = 1〜5 のどれを選んでも変わらない（候補 1・4 は 5/5、候補 2・3 は 0/5）。候補 5 も n1 が成功のため k ≥ 1 なら除外（k = 5 でも 4/5 で 0/k にならない）。したがって k の値の選択は最初の 5 候補の選別に影響しない。
- **制限（評価で引き継ぐ）**: 新版の方向と k は 25 Run の結果を見た後に決めた。上記のとおり選別への影響はないが、結果から独立に決めたことは検証できない。候補 2・3 は 5 回測った分だけ他の候補より厳しく選ばれている（5 回のうち最初の 3 回だけを使う規則で揃える）。この規則でも、評価集合の一部が既に観測した失敗に依存することは解消されないため、結論は §2.2 の「結論の射程」のとおり、固定した候補集合に条件付けて報告する。
- **代替案（採らない）**: order 1 から新版のスクリーニングをやり直す。約 2.3M × 3 回 + 0.33M × 3 回程度の重複費用が掛かり（Evidence からの推測）、同じ条件の観測を捨てる利点がない。

## 5. 予算

### 5.1 (a) 計画値（実測ベースの期待見積もり）

- **スクリーニング（残り）**: 候補 6 以降で 0/3 を 10 件（12 − 2）集める。最初の 5 候補での 0/k の割合 q0 = 2/5 = 0.4（Evidence、5 件のみ）を使うと、必要な候補は約 25 件（推測）。1 候補の期待 Run 数 ≒ 0.6 × 1 + 0.4 × 3 = 1.8（成功候補は 1 回目で成功と仮定。推測）。
  - 25 × 1.8 × 919,103 ≒ **41.4M tokens**
- **評価**: N × rep × (t_T0 + t_T1) × m = 12 × 3 × (68,022 + 150,080.67) × 13.51 ≒ **106.1M tokens**（T1 / T0 = 2.206 が hard Task でも保たれるという仮定は推測）。
- **計画値の合計**: 約 **147.4M tokens**。これは見込みで、上限ではない。旧版の較正 25 Run の 22,977,578 tokens は支出済みで含めない。

### 5.1b (b) 最大許容費用（上限に達した場合）

- **全体上限を置かない場合の構造上の最大**（参考）: スクリーニング（44 − 5 =）39 候補 × 1 候補上限 10M = 390M、評価 12 Task × 1 Task 上限 39M = 468M、合計 **約 858M tokens**。平均ではなく上限どおりに消費した場合の値。
- **推奨**: スクリーニング全体 50M、評価全体 130M の全体上限を置く。キットは「消費済み + 1 Run の上限 > 全体上限」なら次の Run を始めない（較正手順書の既存の動作）ため、消費は全体上限を超えない。したがって今後の追加分の最大許容費用は **180M tokens**（50M + 130M）で、Operator が承認する額はこの 180M とする（(a) の 147.4M を覆う）。支出済みの較正 25 Run（22,977,578 tokens）を含む実験全体の累計の最大は約 **203.0M tokens**。
- 全体上限で止まった場合: スクリーニングで 12 件に届かなければ feasibility-only、評価が途中なら計測不成立で INCONCLUSIVE とし、上限を上げるかは Operator が改めて判断する（結果を見て判定規則は変えない）。
- **候補による偏り**: 0/5 だった候補 2 は 1 Run 2.21M〜3.23M、候補 3 は 0.29M〜0.38M で、平均 m は候補ごとの消費を代表しない。評価費用は選ばれた Task 次第で上下する（候補 2 のような Task だけなら T0 1 Run ≒ 2.6M、T1 ≒ 5.8M と推測）。そのため合計だけでなく候補ごとの上限で管理する。

### 5.2 上限（Human 確定済み）

Operator が 2026-10-27 に推奨どおり確定した（[#244 の確定記録](https://github.com/s977043/dynamic-agent-topology/issues/244#issuecomment-6426773345)）。

| 上限 | 確定値 | 根拠 |
|---|---|---|
| スクリーニングの 1 Run | 4,000,000 tokens、wall clock 30 分 | 現行の承認値。実測の最大 3.23M を収める |
| スクリーニングの 1 候補 | 10,000,000 tokens | 3 回 × 実測の最大の候補（約 2.6M 平均）を収め、異常に重い候補を早く止める |
| スクリーニング全体 | 50,000,000 tokens | 計画値 41.4M に余裕を持たせた値。達したら止める |
| 評価の T0 1 Run / T1 1 Run | 4,000,000 / 9,000,000 tokens（T1 は 2 session 合計） | T1 / T0 = 2.206 を 4M に掛けた値（推測） |
