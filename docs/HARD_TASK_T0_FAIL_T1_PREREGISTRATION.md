## 2. 仮説と判定規則

### 2.1 仮説

- **H1（主）**: スクリーニングで T0 が 0/k だった Task 集合で、同じ Task・同じ条件で T0 を再測定した成功率より、T1 の verified success rate が Δ = 0.30 以上高い。
- **H0**: 差は 0.30 未満。
- **副次（主判定に使わない）**: 成功 1 件あたりの total tokens の T1 / T0、regression rate の差、critical boundary violation の有無、task nature（旧版 U7 と同じく記録のみ）。

**T0 を評価集合で再測定する理由（回帰の対照）**: 「T0 0/k」で選んだ集合には、真の成功率が 0 でない Task が偶然の失敗で混じる。例えば真の成功率 0.2 の Task は k = 3 で 51.2%、0.3 で 34.3%、0.5 で 12.5% の確率で 0/3 になる（計算）。T0 を測り直さずに T1 の成功率だけを見ると、平均への回帰による T0 側の回復を T1 の効果と取り違える。そのため評価では T0 と T1 を同じ Task・同じ rep 数で測り、paired で比べる。スクリーニングの結果は選別にだけ使い、評価の T0 の値には数えない。

### 2.2 判定規則

前提（**計測成立**）: 評価集合 N ≥ 10 Task、完了 block 30 以上、欠測率 ≤ 0.10、全 Run で実効値が V10 と一致、critical boundary violation の検出が機能している。

| 判定 | 条件 |
|---|---|
| **支持** | 計測成立、かつ paired 差の点推定 ≥ 0.30、かつ exact McNemar（片側 α = 0.05）で有意、かつ T1 に critical boundary violation がない、かつ regression rate の差 ≤ 0.10 |
| **棄却** | 計測成立、かつ paired 差の片側 95% 上限 < 0.30（区間は Task 単位で再標本化する cluster bootstrap、10,000 回、seed は確定版で固定） |
| **INCONCLUSIVE** | 上のどちらでもない場合。計測不成立、評価集合が N に届かない（feasibility-only）、評価時の T0 再測定の成功率 ≥ 0.60（難度の操作化の失敗。旧版の p_ceiling と同じ扱い）を含む |

- 棄却でも「T1 に効果がない」とは言わず、「この条件で Δ = 0.30 以上の効果は確認できない」と報告する。
- 支持でも T1 の標準採用の根拠にはしない。採用は独立 Reviewer の Judgment と Human を経る（設計案 §7）。
- 成功 1 件あたりの token 比は、T0 の成功が 0 件なら定義できないため、その場合は block あたりの total tokens の T1 / T0 を報告する。

### 2.3 必要件数の近似（前提は推測）

n = (z_α + z_β)² × (p₁₀ + p₀₁) / (p₁₀ − p₀₁)²、片側 α = 0.05、検出力 0.8、(z_α + z_β)² ≒ 6.19（旧版 §5 と同じ式）。

| 前提（推測） | p₁₀ | p₀₁ | n（block） | rep = 3 の Task 数 |
|---|---|---|---|---|
| T0 再測定 0.10、T1 0.40（推奨の前提） | 0.36 | 0.06 | 28.9 → 29 | **10** |
| T0 再測定 0.20、T1 0.50 | 0.40 | 0.10 | 34.4 → 35 | 12 |

- T0 再測定 0.10 は、0/3 で選んだ集合に偶然の失敗が混じる分を見込んだ推測。block 内で T0 と T1 が独立という仮定も推測で、同じ Task の rep どうしの相関により実効件数は少なくなる。30 block は feasibility-only を外す下限で、検出力の保証ではない。

## 3. スクリーニング

- **手順**: 候補表の初回候補を `order` の昇順で処理する。各候補で T0 を最大 k = 3 回実行し、verified success が 1 回でも出たらその候補は打ち切って除外する（以降の Run をしない）。3 回とも失敗した候補を評価集合に入れる。0/k の候補が N = 10 件そろった時点でスクリーニングを止める。初回 44 件を使い切っても 10 件に届かなければ、評価は feasibility-only とする（予備の追加はしない。V6 の代替案は確定版で判断）。
- **除外の区別**: 1 Run の上限・1 候補の上限・wall clock 上限で止まった Run は「失敗」に数えず、その候補は **budget-excluded** として別記録し評価集合に入れない（成否が分からないため）。環境起因の中止も同じ扱い。
- **k = 3 の根拠**: 打ち切りがあるため成功する候補の費用はほぼ 1 Run で済み、費用の大半は 0/k の候補に掛かる。k = 2 では真の成功率 0.3 の Task が 49% の確率で 0/2 になり、回帰の混入が増える。k = 5 は旧版と同じだが費用が 5/3 倍。推測。
- **止める規則が結果を利用しない理由**: 止めるかどうかは T0 の結果（選別基準）だけで決まり、T1 の結果は見ない。候補の順序は較正前に固定済み（候補表、blob `aad6f23629efaefdd266f0e21ca59248e4693c7b`）。

### 3.1 今回の 25 Run の扱い（推奨: 再利用）

**規則**: 最初の 5 候補は、新版のスクリーニングを済ませたものとして扱う。判定には各候補の **Run 番号の小さい順の最初の k 回（n1〜nk）** だけを使い、n(k+1) 以降の Run は使わない。この規則は 5 候補すべてに同じに適用し、候補ごとに使う Run を選ばない。

- k = 3 での結果: 候補 2・3 は n1〜n3 がすべて失敗で **選別**。候補 1（n1〜n3 成功）・候補 4（同）は除外。候補 5 は n1・n2 が成功のため除外（#244 の 12 Run 時点の表）。
- **結果を見て有利に選んでいないことの確認**: 候補 1〜4 の選別結果は k = 1〜5 のどれを選んでも変わらない（候補 1・4 は 5/5、候補 2・3 は 0/5）。候補 5 も n1 が成功のため k ≥ 1 なら除外。したがって k の値の選択は最初の 5 候補の選別に影響しない。
- **制限（評価で引き継ぐ）**: 新版の方向と k は 25 Run の結果を見た後に決めた。上記のとおり選別への影響はないが、結果から独立に決めたことは検証できない。候補 2・3 は 5 回測った分だけ他の候補より厳しく選ばれている（5 回のうち最初の 3 回だけを使う規則で揃える）。
- **代替案（採らない）**: order 1 から新版のスクリーニングをやり直す。約 2.3M × 3 回 + 0.33M × 3 回程度の重複費用が掛かり（Evidence からの推測）、同じ条件の観測を捨てる利点がない。

## 5. 予算

### 5.1 見積もり

- **スクリーニング（残り）**: 候補 6 以降で 0/3 を 8 件（10 − 2）集める。最初の 5 候補での 0/k の割合 q0 = 2/5 = 0.4（Evidence、5 件のみ）を使うと、必要な候補は約 20 件（推測）。1 候補の期待 Run 数 ≒ 0.6 × 1 + 0.4 × 3 = 1.8（成功候補は 1 回目で成功と仮定。推測）。
  - 期待値: 20 × 1.8 × 919,103 ≒ **33.1M tokens**
  - 最悪（初回の残り 39 候補をすべて 3 回）: 39 × 3 × 919,103 ≒ 107.5M tokens
- **評価**: N × rep × (t_T0 + t_T1) × m = 10 × 3 × (68,022 + 150,080.67) × 13.51 ≒ **88.4M tokens**（T1 / T0 = 2.206 が hard Task でも保たれるという仮定は推測）。
- **合計**: 期待値 約 **121.5M tokens**、最悪 約 196M tokens（107.5M + 88.4M）。旧版の較正 25 Run の 22,977,578 tokens は支出済みで含めない。
- **候補による偏り**: 0/5 だった候補 2 は 1 Run 2.21M〜3.23M、候補 3 は 0.29M〜0.38M で、平均 m は候補ごとの消費を代表しない。評価費用は選ばれた Task 次第で上下する（候補 2 のような Task だけなら T0 1 Run ≒ 2.6M、T1 ≒ 5.8M と推測）。そのため合計だけでなく候補ごとの上限で管理する。
